# Milestone 04 — Failure Recovery and MVP Verification Implementation Plan

> **For agentic workers:** Execute this plan in dependency order. The main agent owns the schema, shared contracts, claiming, retry and recovery semantics, integration, and final verification. Use bounded Calendar, Gmail, and UI subagents only after their interfaces have passed a separate read-only review. A separate read-only critic reviews every implementation task before it is complete.

**Goal:** Recover interrupted runs without replaying confirmed actions, give the owner a safe Gmail-only retry, and verify all nine MVP acceptance criteria through the existing reference workflow.

**Architecture:** Keep the one Node worker and PostgreSQL state machine. Persist when a definitely rejected action may be retried, and reconcile an interrupted Calendar insert by its reserved ID. A Gmail call whose outcome cannot be confirmed becomes `uncertain` and requires an explicit owner request before another send. The web process only records that request; the worker performs the action.

**Tech stack:** TypeScript, Next.js 16/React, Node worker, PostgreSQL with `pg`, `googleapis`, and the existing test runner. No new runtime dependency, queue, service layer, or worker process.

**Spec:** [Product scope](../product.md), [architecture](../architecture.md), [roadmap](../roadmap.md), [decisions](../decisions.md), and the completed [Milestone 03 plan and evidence](03-milestone.md). The owner approved this plan for execution on 2026-10-10, including reviewed incremental local commits; no push or merge.

## Decisions for this milestone

The owner asked the main agent to resolve these Milestone 04 policy choices during planning. They are recorded as decided in the [decision log](../decisions.md) and architecture; the owner may revise them when reviewing this draft plan. No additional product choice needs owner input before implementation. Safe live test resources need owner confirmation at Task 8.

1. **Automatic retry:** At most **three total insert/send attempts per step** in one automatic sequence: the initial attempt plus two retries, scheduled at **1 minute** and **5 minutes** after a _definitely rejected_, rate-limited attempt. The existing 60-second worker cycle processes a retry no earlier than `next_attempt_at`; it does not sleep in a request. Only HTTP `429`, or HTTP `403` with the documented `rateLimitExceeded` or `userRateLimitExceeded` reason, qualifies. Other `400`–`404` authorization/configuration failures are final. Treat transport errors, timeouts, `5xx`, `409`, and success without a required ID as **unknown**, never as a definite rejection. Keep Google SDK retries disabled. This intentionally favors avoiding duplicate side effects over retrying every transient error. [Gmail error guidance](https://developers.google.com/workspace/gmail/api/guides/handle-errors); [Calendar error guidance](https://developers.google.com/workspace/calendar/api/guides/errors).
2. **Calendar reconciliation:** Before **any** repeat insert, call `events.get` on the **saved Calendar ID and reserved event ID**, with SDK retry disabled. A found event matching the saved title, notes, start, and end confirms Calendar success. A found but mismatched event stops as `calendar: uncertain`. After a definitely rejected transient insert, a successful not-found lookup permits one repeat insert with the **same** reserved ID when its backoff is due. After an **unknown** insert outcome, a not-found lookup is only an observation, not proof that no event exists; make at most three read-only lookups, separated by 1 and 5 minutes, then stop as `calendar: uncertain` and `run: failed`. A retryable lookup error uses the same bounded read-only schedule; a permission error or lookup still unresolved after that schedule stops for owner review. No Calendar retry control is offered. This is conservative because a Calendar `404` can also mean lack of access and Google does not guarantee event-ID collision detection. [Calendar errors](https://developers.google.com/workspace/calendar/api/guides/errors); [event ID rules](https://developers.google.com/workspace/calendar/api/v3/reference/events).
3. **Gmail-only manual retry:** On a `partially_failed` run with Calendar `succeeded` and Gmail `failed` or `uncertain`, show a retry form. For `uncertain`, the form states that the previous message may have been sent and a repeat may send a duplicate; require a fresh, unchecked-by-default acknowledgment for **each** request. The server action rejects an absent acknowledgment and transactionally enqueues **one** Gmail-only attempt. A definite failure needs no duplicate warning. The worker sends from the saved snapshot; it does not touch Calendar. A manual request is one attempt, with no automatic retry cascade; another failure needs another explicit request. Repeated POSTs cannot enqueue parallel sends. A request made while the workflow is disabled stays queued until it is enabled; it never bypasses the worker's enabled check. No Gmail inbox or Sent search is added under the existing `gmail.send` scope.
4. **Single active worker:** Hold one PostgreSQL session advisory lock on a **dedicated, pinned client** for the whole poll/recover/execute cycle. If another worker owns it, skip the cycle. If that connection errors or ends, stop the cycle and start **no further Google calls**. A call already in flight may finish after the lock is released, so the next worker must treat each persisted `running` boundary conservatively, including a possibly in-flight action; it never infers that lock release proves the action did not happen. This is a local single-owner process guard, not hosting or supervision design.

## Shared persistence and interface contract — Task 1, main agent only

Task 1 must freeze this contract, pass its own tests, and receive a separate read-only review **before** Tasks 3, 4, or 7 are delegated. Later changes to the contract return to the main agent for review before dependent work continues.

**Migration `db/004_recovery.sql`:** Extend `step_run` with nullable `next_attempt_at timestamptz`, `retry_mode text NOT NULL DEFAULT 'automatic' CHECK (retry_mode IN ('automatic','manual'))`, and `lookup_attempt_count integer NOT NULL DEFAULT 0 CHECK (lookup_attempt_count >= 0)`. Keep `attempt_count` as the number of durable action starts, including manual ones; it increments **before** a possible API call, so a crash can count an attempt that never reached Google. A Calendar read-only lookup does not increment it. Existing rows retain their states, IDs, timestamps, snapshots, and poll cursors. `run.state` retains the Milestone 03 values: `queued`, `running`, `filtered_out`, `succeeded`, `failed`, `partially_failed`. No attempt-history table is required; the detail shows the current outcome, attempt count, and next due time.

**Action interface in main-owned `src/lib/run-execution.ts`:** Add `retryable?: boolean` to rejected failures, with absence interpreted as `false` so the existing Milestone 03 adapters typecheck before Tasks 3–4; `unknown` has no retryable flag. Tasks 3–4 return an explicit boolean for every rejected result. Keep the existing `CalendarClient.insertEvent` contract and add a separate `CalendarLookupClient` with `lookupEvent(input: CalendarEventInput): Promise<CalendarLookupResult>`; Task 5 takes `CalendarClient & CalendarLookupClient`. This keeps existing Milestone 03 insert-only test doubles valid while the adapter task is pending. `CalendarLookupResult` is `{ kind: 'found_match'; eventId: string } | { kind: 'found_mismatch' } | { kind: 'not_found' } | { kind: 'unavailable'; code: string; message: string; retryable: boolean }`. The adapter returns fixed safe errors and never returns event contents. The lookup must compare the event's ID and mapped title, description, start, and end with the run's saved action input; compare date-times as instants, not raw offset strings. A `404` is `not_found` only when the chosen Calendar itself remains accessible; otherwise `unavailable`. No Google call occurs in a database transaction.

**Run detail and mutation interface:** Extend `RunDetail.steps[]` with `nextAttemptAt: Date | null`; add `workflowEnabled: boolean` for a clear paused-while-disabled cue. Expose `gmailRetry: 'none' | 'definite' | 'uncertain'` computed from persisted run/step states, never from client input. Add main-owned `requestGmailRetry(runId: string, acknowledgeDuplicateRisk: boolean, db = getDb()): Promise<'queued' | 'not_allowed' | 'warning_required'>`. It locks the run and Gmail step, requires Calendar `succeeded`, Gmail `failed` or `uncertain`, and run `partially_failed`; for `uncertain` it requires `acknowledgeDuplicateRisk === true`. It changes only Gmail to `pending` with `retry_mode='manual'`, `next_attempt_at=now()`, clears its current safe error, and changes the run to `queued` with cleared terminal time/error. The confirmed Calendar ID and step stay unchanged. A second request while queued or running returns `not_allowed` without changing state.

**State and claim rules:** `queued` plus no `step_run` rows means a newly detected run. `queued` plus existing rows means a scheduled retry or explicit Gmail-only request; only the due `pending` action may run. One claim transaction locks run and workflow rows, checks `enabled`, `next_attempt_at <= now()` where present, marks run `running`, and creates step rows only for a new run. Existing `succeeded` steps are never restarted. A definitely rejected transient action sets its step back to `pending` with the due time and `retry_mode='automatic'`, retains its safe rate-limit reason, sets run `queued`, and clears terminal time/error. A final Calendar rejection makes run `failed` and Gmail `skipped`; a final Gmail rejection makes run `partially_failed` and retains Calendar success. A manual Gmail request follows the mutation contract above and is ineligible for automatic follow-on retry. After a crash, `running` with Filter `pending` resumes Filter and validation; Filter `succeeded` with Calendar `pending` rebuilds inputs from the snapshot and starts Calendar only after any required pre-retry lookup; Calendar `succeeded` with Gmail `pending` resumes Gmail only. A due Calendar retry whose pre-insert lookup is unavailable increments `lookup_attempt_count` and uses the same three-lookup, 1-minute/5-minute schedule, then stops uncertain; it never inserts on that observation. `running` Calendar with a reserved ID is reconciled read-only; `running` Gmail after interruption becomes `uncertain` and `partially_failed` with no send. A Gmail success and run success are one transaction. A found matching Calendar event is persisted as success before Gmail starts. Reconciliation delay uses `next_attempt_at` while the run remains `running`; it may finish after disable because it was already in progress.

**Important legacy boundary:** A null-snapshot run is never claimed or retried. Do not modify the Forms response uniqueness constraint or poll cursor rules. The UI must not offer retry for a legacy run or an unresolved Calendar step.
